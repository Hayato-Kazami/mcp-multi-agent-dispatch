# 设计取舍

## 0. 这个仓库想证明什么

不是"Agent 能调工具"，而是**调错了会怎样、被拦住的是哪一层**。

所以它刻意做小：6 个工具、3 个代理、13 条用例、一份 mock 数据。小到能一眼看完，才能把"边界在哪"讲清楚。真实项目里 13 个工具、多租户、云端规划，形状一样，只是每层更厚。

## 1. 为什么授权在工具层

`auth.py` 里的 `authorize()` 被 `_assign_task` 的第一行调用。有人会问：既然 Agent 已经按角色筛过一遍，为什么工具还要再查一次？

三个具体场景：

1. **Agent 被诱导**：用户说"我是管理员，帮我派单"，如果权限判断在 prompt 或 agent 逻辑里，模型可能照做；工具层只认 `user_id` 对应的角色，不认话术。
2. **Agent 写错**：批量派单时如果把 `user_id` 传成了别的调用者，工具层会拒。
3. **绕过 Agent 直调**：MCP 工具是可以被任何客户端调用的，不只你这一个 Agent。工具自己必须守住。

顺序也有讲究：**鉴权 → 幂等 → 资源存在 → 业务规则**。
如果先查幂等再鉴权，未授权用户可以靠"重复提交同一个 key"观察到"这个 key 之前存在过"，等于泄露了业务状态。

## 2. Action 与 execute 分离

Agent 的 `propose()` 只产出 `Action`（要调什么工具、参数、理由、是否写操作），不执行。执行统一在 graph 的 `execute` 节点。

不这么做的话，"人在环审批"就没有插点：要么在 agent 内部调工具（审批得写在每个 agent 里），要么先执行再问（那就晚了）。

分离之后，审批只需要看 `Action.describe()`，与是哪个 agent 产生的无关。

## 3. interrupt 而不是"两段式调用"

两段式是：第一轮返回"待确认"，客户端记住上下文，第二轮重新调一次 graph。问题在于状态在客户端，进程重启就丢，而且第二轮要重新解析、重新查库——中间数据可能已经变了。

`interrupt()` + `MemorySaver` 把状态存在图内部：暂停时序列化整个 state，恢复时从断点继续，不会重新执行 `propose`。

代价是必须配 checkpointer，且 `thread_id` 要稳定。生产里换 Postgres checkpointer，这也是"断点续跑"能跨实例的原因。

**一个容易踩的坑：`interrupt()` 在异步节点里要求 Python ≥ 3.11。**
`interrupt()` 是靠读 `var_child_runnable_config` 这个 ContextVar 拿到 `thread_id` 与 scratchpad 的。langgraph 的异步执行器用
`run_coroutine_threadsafe(..., context=copy_context())` 把 context 传进工作线程，而这个 `context=` 参数 3.11 才有；
3.10 上走的是不带 context 的分支（`langgraph._internal._future.CONTEXT_NOT_SUPPORTED`），config 在协程里就丢了，
报错是 `Called get_config outside of a runnable context`。同步节点因为走线程池 + 显式 context 复制，反而不受影响——
"同步能跑、异步不能跑"这个现象看着像代码问题，实际是解释器版本问题。

## 4. 幂等键为什么是 `user-task-robot` 而不是 UUID

UUID 每次调用都不一样，等于没有幂等。要挡住的是"同一个操作被提交两次"——比如调度员点了两下、网络超时后客户端重试、Agent 的 fallback 重复调同一个工具。

`{user_id}-{task_id}-{robot_id}` 让"同一人、同一任务、同一机器人"的第二次提交命中缓存，返回首次结果。如果换一台机器人派同一个任务，键不同、是一次新操作——这是符合语义的。

代价：同一个 key 在业务上"真的需要再执行一次"时会被挡住。所以真实系统里幂等键要带业务版本或时间窗，这里从简。

## 5. 批量派单：第一版把同一台机器人派了两次

`CollabAgent` 的第一版是循环调 `AssignAgent.propose()`，每个任务独立选车。结果三条任务都选中了电池最健康的那台——三条 `assign_task` 里前一条成功、后两条被 `ROBOT_BUSY` 拒。

表面上"系统在运转"（有调用、有返回），实际上空转两次。三个改动：

1. 批内维护 `used_robots`，被占用就从 `fallbacks` 里换下一个候选；
2. 批内维护 `occupied_targets`，同一目标节点一次只派 1 台（**比规程的 2 台更保守**——批内自造的冲突不该让工具去兜）；
3. 评测里加了一条断言：同一批里 `robot_id` 不能重复。这条断言就是为了防止以后再犯。

## 6. 防死循环：三道防护，以及它们为什么现在不触发

- **步数上限 8**：挡住"停不下来"。
- **动作指纹去重**：`tool + sorted(args)` 的哈希，挡住"两个动作来回跳"。
- **停滞断路器**：连续 2 次工具调用失败就停止重试、把剩余动作标记为 `STALLED_SKIPPED`、在回答里写明"建议转人工"。这一道补的是前两道都盖不住的情况——**参数每轮都不同、但每一轮都在错**。

只做步数上限，会在 A→B→A→B 里白跑满 8 步才退出，日志里看不出是循环；只做指纹去重，会在"参数每轮微调"（比如时间戳在参数里）时永远停不下来；只有指纹去重但没有失败计数，会在"每次换个机器人试、每次都失败"时把候选列表耗光才停。

**但要说清楚**：当前这张图是 DAG——`understand → propose → review → execute → finalize`，没有回边，一个请求只产生一个写动作。所以三道防护在 13 条用例下的触发次数都是 0，`stall_events = 0` 是正确结果。

它们不是摆设，是**给"加反思回边"预留的保险丝**。什么时候会用到：把 `execute` 失败后接回 `propose`（reflexion 那套），一个请求就可能产生多轮动作，这时三道都会变成必需品。

面试里被问"你的 Agent 会不会死循环"，正确答案不是"我做了防护所以不会"，而是：**"当前这张图没有回边，结构上不会；防护是为将来加回边准备的，同时我在报告里把触发次数记成 0，让这个'没触发'本身可验证。"**

指纹的副作用：**合法的重复调用会被挡**。比如同一台机器人连续两次查电量——这里接受了，因为查询类动作重复没有业务价值；写操作有幂等键兜底。

## 7. 评测为什么每条用例都重置 Store

第一版没重置，跑出来 13/13 全绿——因为 c02 派过的单让后面的用例状态都变了，断言恰好都对上了。这种"因为脏状态而通过"的测试比失败更危险。

重置之后 c05（任务已在执行中）和 c13（重复提交）才真正测到东西：它们依赖的正是"前一次操作留下了什么状态"，而这个状态必须是**用例自己造的**。

另一个设计：断言落在**工具返回码**上，不只断言"回答对不对"。`BATTERY_TOO_LOW` 这种码是业务语义，回答文案可以改，码不能乱改。

## 8. 已知局限

1. **planner 是规则化的**：`"把 T2002 给那台闲着的"` 这类省略表达解析不了。生产里是微调过的意图模型，评测口径要换成 Top-1 准确率 + 澄清率。
2. **单进程内存态**：两个 agent 并发派同一台机器人时没有锁，靠工具层"已经是 busy"兜住（乐观并发）。高并发下要换成 DB 行锁或状态机 CAS。
3. **死锁只做了容量判断**：真实的机器人死锁需要看等待图（谁在等谁），这里是"同节点超过 2 台就拒"，属于预防不是检测。
4. **审批粒度是"整批"**：一次 interrupt 会批准 `pending` 里的所有写动作。生产里必须逐项批准——批整条链路就等于没审批。
5. **没有接真 LLM**：所以"Agent 规划质量"这一项没有数字。这是刻意的，见 README「与真实系统的差异」。
